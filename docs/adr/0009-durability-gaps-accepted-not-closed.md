# 兩個已知的 durability 缺口：接受而非修補

任何稽核這個系統的讀者都會很快找到這兩個洞，因此把它們記錄成決定，而不是留著看起來
像疏漏。

**雙寫。** 一份 Job 先提交到資料庫，再作為另一個步驟投遞給 broker；兩者之間發生崩潰，
會留下一份已被 accept 卻從未被投遞的 Job。教科書的解法是 transactional outbox。我們
不建置它，因為更便宜的做法是偵測並修復而非預防：定期掃描已超過門檻仍未被取走的 Job
並重新投遞。程式碼少得多，而且它本身會產出一個值得監控的復原計數。

**沒有 idempotency key。** submitter 在回應遺失後重試，會建立重複的 Job。我們接受
這件事：submitter 是我們自己的網頁介面與我們自己的 Batch Submitter，而一次重複的代價
是一次浪費的轉錄，不是資料損毀。這個代價目前不足以支撐那個機制。

當系統開始接受我們控制不了的 client 提交，或當浪費的下游費用不再可以忽略時，兩者都
應重新開啟。
