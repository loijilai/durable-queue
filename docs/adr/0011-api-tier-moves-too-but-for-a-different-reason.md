# API tier 也一起遷移 —— 但理由不同，而且不加 scaling policy

Worker 遷移到容器編排，是因為容量決策需要一根粒度正確的控制桿。API tier 沒有這個
需求：它以固定容量運行是為了可用性，不是為了彈性。它仍然一起遷移，而理由值得與
Worker 的理由分開陳述，好讓日後沒有人推論出一個從來不是論據的對稱性。API tier 目前
的部署方式是開一台虛擬機、對它跑一段 shell 腳本；task definition 是同一件事的宣告式
版本。這是單純的簡化，不是為了對齊。

它不設 scaling policy。沒有任何量測指出需要它，而「沒有證據就加機制」正是這個專案
試圖避免的習慣。

## Consequences

資料庫遷移從 API 的啟動指令中抽出，成為滾動部署之前執行的一次性 task。這原本就是一個
潛伏的競爭條件 —— 數個實例可能同時執行遷移 —— 而滾動部署只會讓它更容易發生，不會
更不容易。

零停機部署不再依靠實例更換達成，改為依靠帶有最低健康百分比的滾動更新。這是等價替換；
藍綠部署與金絲雀部署刻意不隨之引入，它們沒有任何需求需要回答。
